# T3 Code tools

This stack runs in T3 Code, in Claude and Codex threads. This file is the
reference for how its skills use T3's tools. Read it once per session, before
the first time you start an agent, wait on one, or reach for a T3 tool.

`<ferret-mode>` is the real path (`readlink -f`) of the folder that holds this
file, not a symlink to it. `<stack>` is the repository root, two folders above
it. Use these absolute paths in every brief.

T3's tools are the `t3-code` MCP tools (`mcp__t3-code__<tool>` in Claude).
Some load late. In Claude, load one with `ToolSearch` (`select:<full name>`)
before its first call, and try a tool once before you decide it is missing.
When a step needs a tool this session does not have, put one line in your
reply, `Skipped: <step>. <reason>.`, and go on to the next step. Do not stop,
ask, or retry.

## Starting agents

Every spawn in this stack (a `poteto-agent`, a panel seat, a swarm worker, a
judge) goes through `delegate_task`. The one exception is a quick foreground
helper on your own provider and model with no setting changes, which may use
the native subagent (`Agent` in the foreground in Claude, `spawn_agent` in
Codex). Never start a background `Agent`.

Every `delegate_task` call gets:

- a `title` (what the child does), a `role` (`implementation`, `research`,
  `review`, `design`, `test`, or `general`), and a unique `clientRequestId`;
- `mode: "async"`, the default;
- a `target` from the role's line in the models file (see Models), or none
  for `inherit-parent`;
- a `task` whose first line is `Read <ferret-mode>/worker.md before anything else.`,
  then the goal, the task, and file paths rather than pasted content.

Keep each returned `taskId`. Never put a secret in `task`. To start N agents
at once, make N `delegate_task` calls in one message.

| Kind of agent | How |
| --- | --- |
| `poteto-agent` (a helper that works in ferret-mode's style) | `role: "implementation"` (or the role that fits), and the `task` opens with two lines: `Read <ferret-mode>/worker.md before anything else.` and `Then read <ferret-mode>/SKILL.md in full, including its Principles index, and <ferret-mode>/t3.md.` |
| Comment Sicko (comment reviewer) | `role: "review"`, and the `task` opens with `Read <stack>/agents/comment-sicko.md and act as it.`, then the files or diff to review. |
| Plain worker | The worker.md line first, then the brief. |
| Read-only helper | `role: "review"` or `"research"`, and the brief says "Read-only on the user's checkout: do not edit, commit, or push anything there." In its own worktree it may still write repros and commit them on its own branch, and it never pushes. After it finishes, check `git status` on the user's checkout yourself. |
| Agent in its own checkout | `isolation: "worktree"`. See Worktrees. |
| Agent in the user's checkout | `isolation: "shared"`, the default. Give each one its own output folder. |
| Agent that starts from another pushed branch | `isolation: "worktree"`, and the brief's first step is `git fetch origin <b> && git checkout -B <b> origin/<b>`. |
| A follow-up or retry | A fresh `delegate_task` with the original brief, every later directive, and the earlier report pasted in. |
| A new top-level thread | `t3_thread_launch`, only when the user asks for a new thread. |

## Waiting and results

- Do not poll a child, sleep, or loop. Its completion wakes your thread. While
  children run, do work that does not depend on them, and end your turn when
  none is left.
- A phase that needs every child (arena's cross-judge, swarm's aggregate)
  starts on the wake of the last one. On each earlier wake, read that result,
  note it, and end the turn again.
- The wake carries the child's final report. For more, use `t3_thread_read` on
  its `childThreadId`. Name a child to the user by its `link`, verbatim.
- Stop a child you no longer need with `task_cancel`. A finished child keeps
  its result. Never use `t3_thread_interrupt` on a child.
- Each new review round is a new `delegate_task`, never `t3_thread_send`.
- To wait on a long command you started in the background (a build, a test
  run), call `t3_background_wait` with its task ID.

## Worktrees

- A worktree child starts from the parent's last commit. Uncommitted edits stay
  out. When a brief needs them, such as interrogate's scope, write them with a
  throwaway index, so the user's own index is never touched:

  ```bash
  idx=$(mktemp) && cp "$(git rev-parse --git-path index)" "$idx" \
    && GIT_INDEX_FILE="$idx" git add -A \
    && GIT_INDEX_FILE="$idx" git diff --cached --binary HEAD > <scratch>/scope.patch; rm -f "$idx"
  ```

  This includes new untracked files. Make `git apply --allow-empty <scratch>/scope.patch`
  the brief's first step. `--allow-empty` keeps a clean tree from failing.
- A scope that is a committed range ending before `HEAD` (`<a>..<b>`) needs no
  patch. The brief's first step is `git checkout --detach <b>`.
- Each worktree child commits its work on its own branch and reports the
  absolute worktree path, the branch, and the commit SHA. Read candidates from
  there, or with `git diff <base>..<branch>` from your checkout.
- T3 keeps worktrees under `~/.t3/worktrees/<project>/`.

## Models

`/setup-ferret-stack` writes `~/.config/ferret-stack/models.md`. Read it before the
first spawn of a session. Each line is `role: value`, and a value is one target
or a comma-separated list of targets:

```
<providerInstanceId>/<model id> <option id>=<value>
claudeAgent/claude-opus-5-5 effort=xhigh
codex/gpt-6-luna reasoningEffort=high
antigravity/gemini-4-neon thought_level=xhigh
inherit-parent
```

A target becomes `target: {providerInstanceId, model, options: {<option id>: <value>}}`.
`inherit-parent` or `auto` means: omit `target`, so the child runs on your
model. A role with no line, or no file, uses the default in the skill.

Option names differ by provider: Claude uses `effort`, Codex
`reasoningEffort`, and Antigravity `thought_level`. Check them, and which
providers are enabled, with `orchestrator_capabilities` once per thread before
the first `delegate_task`. No role runs above `xhigh`. Fast mode stays off
unless the user asks for it.

When a target's provider is disabled or its model is missing, use the closest
model of the same family that `orchestrator_capabilities` lists, then the
skill's fallback, then drop the seat. Say which. A panel keeps at least two
seats from different vendors.

A provider can be listed as enabled and still fail when the child starts, for
example `Failed to open … provider session` or `provider_unavailable: … not
authenticated`. Retry that seat once with a new `clientRequestId`. If it fails
again, treat the provider as unavailable for the rest of the session and
apply the fallback above. Tell the user once which provider failed and why,
since signing in is theirs to do.

**Vendor** comes from the model id, not the provider: `claude-*` (Fable
included) is Anthropic, `gpt-*` is OpenAI, `gemini-*` is Google, and `grok-*`
is xAI. Antigravity can also run Claude models, and those still count as
Anthropic.

## Other tools

| Need | Tool |
| --- | --- |
| A todo list | `TodoWrite` in Claude or `update_plan` in Codex, when the session has it. T3 threads often do not. Then keep the list in your reply, numbered, and restate it with marks at each phase. |
| A question for the user | `AskUserQuestion` in Claude. Otherwise ask in plain text. A child never asks. It decides and reports, per worker.md. |
| Keep working for hours, or wake up later | Keep going in the turn while there is work. To come back later, use `schedule_task` with `{type: "interval", everyMs}` or `{type: "once", runAt}` and `bindToCurrentThread: true`. Never sleep or poll in a loop. |
| A job on a schedule or triggered from outside | `schedule_task` (fixed time, interval, once, or `{type: "webhook"}`). |
| A password, token, or code only the user knows | `request_secret`. |
| Rules that apply to every session | `CLAUDE.md` in Claude, `AGENTS.md` in Codex. |
| Skills | User skills: `~/.claude/skills/` and `~/.codex/skills/`. Project skills: `.claude/skills/<name>/`, plus a symlink at `.agents/skills/<name>` for Codex. This stack's skills are linked into the user folders by `<stack>/scripts/install.sh`. |
| Past chats (for recall, session pickup, automate-me, eval) | T3 threads: `t3_thread_search`, then `t3_thread_read`. Raw files: Claude Code at `~/.claude/projects/<slug>/*.jsonl` (the slug is the path with `/` and `.` turned into `-`), and Codex at `~/.codex/sessions/<yyyy>/<mm>/<dd>/*.jsonl`. Read only the workspace's own history. |
| Open or update a PR | `gh`. After you create or push to a PR, call `link_pull_request` with its URL. |
| Wait on PR checks or reviews | `watch_pull_request`, then end your turn. T3 wakes you on failed checks, new comments, or conflicts. Do not call it again on a wake. For a one-shot status, use `gh pr view <pr> --json statusCheckRollup,reviewDecision,mergeable` and `gh pr checks <pr>`. Call `unwatch_pull_request` before you hand back. |
| Review bots on a PR (such as CodeRabbit or Copilot review) | Their comments are ordinary review threads. Triage them per `<ferret-mode>/references/review-bot-triage.md`. |
| Drive a web, browser, or Electron UI | `preview_open`, `preview_snapshot`, `preview_act`, and `preview_wait_for`, or Playwright. Close any tab you opened before you reply. |
| Drive a CLI or TUI | Run it in the shell, or in `tmux` for an interactive TUI, and read the output. |
| Simulators and devices | `device_open`, `device_screenshot`, and `device_close`. |
| Show a chart, diagram, or visual summary | `html_preview`, then `html_render` with the returned height. A picture the user wants to keep is a `.png` file and its path. |
